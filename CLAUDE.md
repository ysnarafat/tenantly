# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## 📋 Project Overview

**Tenantly** = property rental management system, Bangladesh market. Full-stack, three components:

- **Backend API**: Go (Gin) at `src/backend/api` - core business logic
- **Frontend**: Angular 21 at `src/frontend` - standalone components, Material Design
- **Notification Service**: .NET background service at `src/backend/notification-service` - SMS/Email alerts

PostgreSQL for storage. Docker Compose for local dev.

## 🏗️ Architecture & Structure

### Backend (Go) - Layered Architecture

```
internal/
├── models/          # Domain entities (User, Property, Unit, Lease, etc.)
├── repositories/    # Database access layer (CRUD, queries)
├── services/        # Business logic & use cases (orchestrates repositories)
├── handlers/        # HTTP handlers (request/response mapping)
├── middleware/      # Auth, logging, error handling
├── config/          # Environment & database configuration
├── database/        # DB connection & migration utilities
├── db/              # sqlc-generated query code (DO NOT EDIT manually)
├── server/          # Gin server setup & routing
└── testutil/        # Integration test DB helpers

cmd/
├── server/          # Main API server entry point
└── migrate/         # Database migration CLI tool

migrations/          # SQL migration files (versioned)
sql/queries/         # sqlc query definitions (payment.sql only)
```

**Key Patterns:**
- All cross-layer dependencies are interfaces defined centrally in `internal/interfaces/interfaces.go`. Concrete implementations wired in `cmd/server/main.go`.
- Services receive repository interfaces via DI; handlers receive service interfaces via DI.
- Building module split pattern: `building_repository.go` (CRUD) + `building_repository_analytics.go` (analytics) + `building_validation_service.go` (validation) — follow for large modules.

**sqlc vs raw SQL:**
- `internal/db/` is generated by sqlc from `sql/queries/payment.sql` — covers simple payment CRUD only. Run `sqlc generate` after editing that file.
- All complex queries (multi-table joins, dynamic filters, aggregations) live in `*_raw.go` files alongside the repository (e.g., `payment_repository_raw.go`). Prefer this pattern for new analytical or filtered queries.

**Handler utilities (defined in `handlers/payment_handler.go`, used across handlers):**
- `parseDateRange(c *gin.Context) (time.Time, time.Time, error)` — parses `start_date`/`end_date` query params (YYYY-MM-DD), defaults to last 30 days when omitted.

### Org-scoping middleware

Every route group that deals with org data must include `middleware.RequireOrgContext()`. This middleware (defined in `internal/middleware/auth.go`) reads `organization_id` from the JWT claims and injects it as `"org_id"` (int) into the Gin context. Handlers read it with `c.GetInt("org_id")`.

```go
// Example route group setup in server.go
group := protected.Group("/reports")
group.Use(middleware.RequireOrgContext())
{
    group.GET("/ledger", middleware.RequireAnyRole(), reportHandler.GetFinancialLedger)
}

// Handler reads org_id
orgID := c.GetInt("org_id")
```

### Interface maintenance invariant (critical)

Adding a method to any repository interface in `interfaces/interfaces.go` **immediately breaks compilation** of every file that holds a mock struct for that interface. The main one is `MockPaymentRepo` in `internal/services/payment_service_test.go`. Always add a stub implementation there when extending `PaymentRepositoryInterface`.

```go
// Stub pattern used in payment_service_test.go
func (m *MockPaymentRepo) NewMethod(args...) (ReturnType, error) {
    return zero, nil
}
```

### Frontend (Angular) - Standalone Components with Feature-Level State

```
src/app/
├── core/            # Singletons: services, guards, interceptors
│   ├── services/    # API clients, auth, state management
│   ├── guards/      # Route guards
│   ├── interceptors/# HTTP interceptors
│   └── models/      # Shared TypeScript interfaces
├── features/        # Feature modules by domain
│   ├── [feature]/
│   │   ├── [name].ts              # Standalone component (no .component suffix)
│   │   ├── [name].html            # Template
│   │   ├── [name].scss            # Styles with theme support
│   │   └── store/                 # Optional: Feature-specific NgRx store
└── app.routes.ts    # Route definitions (all routes use loadComponent lazy loading)
```

**Key Patterns:**
- Standalone components (no NgModule). All routes use `loadComponent: () => import(...).then(m => m.ComponentClass)`.
- Global state via NgRx in `src/app/store/`; features can have their own store under `features/[name]/store/`.
- Services use RxJS observables. Prefer `signal()` and `computed()` over traditional change detection.
- Material Design for UI. Environment files for config.

## 💾 Database

- **System**: PostgreSQL
- **Driver**: `lib/pq` (Go)
- **Migrations**: golang-migrate (versioned SQL in `migrations/`)
- **Migration Commands**:
  ```bash
  cd src/backend/api
  go run cmd/migrate/main.go up   # Apply pending migrations
  ```
  Migrations also run automatically on server startup.
- **Creating migrations**: Add files as `migrations/NNNNNN_description.up.sql` and `migrations/NNNNNN_description.down.sql`, where `NNNNNN` is the next sequential number (zero-padded to 6 digits, e.g. `000010`).

## 🔐 Authentication & Authorization

**Type**: JWT (JSON Web Tokens)

**Backend**:
- Tokens generated in `internal/handlers/auth.go`
- Middleware validates in `internal/middleware/`
- Claims include user ID, role, and organization ID
- Reference: `src/backend/api/AUTHENTICATION.md`

**Frontend**:
- Tokens stored in localStorage
- HTTP interceptor attaches token to requests
- Auth guard protects routes

**Current Roles & Multi-Tenancy** (5-level hierarchy):
- `SUPER_ADMIN` - Platform level, manages organizations
- `ORG_ADMIN` - Organization level, manages org users
- `Admin` - Organization data management
- `PropertyManager` - Property-level operations, building/unit management
- `Accountant` - Read-only financial access

Role constants live in `internal/middleware/auth.go`. Middleware helpers: `RequireSuperAdmin()`, `RequireOrgAdmin()`, `RequireAdmin()`, `RequireAnyRole()`.

## 🌐 Internationalization (i18n)

Frontend supports **English** and **Bangla** translations using **ngx-translate**.

Translation files: `src/frontend/src/assets/i18n/en.json` and `bn.json` — must always be kept in sync (same keys, same structure).

All keys use 3-level hierarchy: `NAMESPACE.SECTION.KEY`. The `COMMON` namespace holds shared UI vocabulary (buttons, errors, pagination) used across features.

```typescript
// In component TypeScript with TranslateModule imported:
@Component({
  imports: [TranslateModule],
  template: `<h1>{{ 'LEASE_LIST.PAGE_TITLE' | translate }}</h1>`
})
```

### Screens with Translations

✓ Complete: Dashboard, Lease List, Tenant List, Property List, Unit/Building Form Dialogs, Due List, Reports & Analysis

❌ Incomplete (hardcoded text): Organization Management, User List, Attachment List, Payment List

### Adding New Translations

1. Add key to **both** `en.json` and `bn.json`
2. Use in template: `{{ 'NAMESPACE.SECTION.KEY' | translate }}`
3. Run `npm run build` to verify

## 🎨 Frontend Styling & Theming

Frontend supports light/dark themes via **CSS variables** — runtime switching without reloads.

```scss
// In component SCSS files:
:root,
[data-theme='light'] {
  --bg-primary: #ffffff;
  --text-primary: #1a1a1a;
  --color-primary: #1e88e5;
}

[data-theme='dark'] {
  --bg-primary: #121212;
  --text-primary: #ffffff;
  --color-primary: #64b5f6;
}

.component {
  background-color: var(--bg-primary);
  color: var(--text-primary);
  transition: background-color 0.3s, color 0.3s;
}
```

Theme is toggled by setting `data-theme` attribute on `document.documentElement` and persisted in localStorage. See `dashboard.scss` and `property-card.scss` for reference.

**Component styling guidelines:**
- Group theme variables at top; order: variables → mixins → base styles → responsive queries
- Breakpoints: `@media (max-width: 768px)` (tablet), `@media (max-width: 480px)` (mobile)
- All interactive elements need `:hover`, `:focus`, `:active` states

## 🧪 Testing Strategy

### Backend (Go) — two distinct patterns

**Service-layer unit tests** (e.g., `internal/services/payment_service_test.go`):
- Inline `Mock*` structs that implement repository interfaces
- No real DB — fast, run anywhere
- Pattern: `func (m *MockPaymentRepo) MethodName(...) { return stubValue, nil }`

**Repository integration tests** (e.g., `internal/repositories/payment_repository_test.go`):
- Use `testutil.SetupTestDB(t)` which connects to a real PostgreSQL instance and runs all migrations
- Hardcoded defaults: `localhost:5432`, user `user`, password `p@ssw0rd`, database `tenantly_test`
- Helpers in `testutil/database.go`: `CreateTestProperty`, `CreateTestBuilding`, `CreateTestUnit`, `CreateTestTenant`, `CreateTestOrganization`
- Require a running PostgreSQL with the `tenantly_test` database created

```bash
# Run only unit tests (no DB required)
go test -v ./internal/services/... ./internal/handlers/...

# Run integration tests (requires DB)
go test -v ./internal/repositories/...
```

### Frontend (Angular)
- Jasmine/Karma framework, tests in `.spec.ts` files alongside components
- Run: `npm test`

## 🤖 Claude Code Behaviour

- **Commit authorship**: Never add a `Co-Authored-By` trailer to any commit, and never attribute a commit to any Claude/Anthropic model. Commits show only the human author's authorship.
- **Commit body**: Do not write a commit body by default — use a single-line subject only. Only when a change genuinely requires a body (e.g. non-obvious rationale, breaking change, migration notes) should one be added, and in that case ask the user for confirmation before including it.
- **Format before committing (required)**: CI runs `prettier --check` (frontend) and `gofmt -s -l` (backend) over the whole tree, so any unformatted file fails the check. Before committing, always format the files you touched:
  - Frontend: from `src/frontend`, run `npm run format` (or `npx prettier --write <files>`). Prettier config: single quotes, `trailingComma: es5`, `printWidth: 100`, LF line endings.
  - Backend: from `src/backend/api`, run `gofmt -s -w <files>` (or `gofmt -s -w .`).
  - Line endings are LF everywhere (enforced by `.gitattributes`). On Windows, `core.autocrlf=true` makes the working tree CRLF — that is normal and CI is unaffected; do not "fix" phantom CRLF diffs that `git ls-files --eol` shows as `i/lf`.

## ⚠️ Common Issues & Notes

- **Frontend**: Angular 21 standalone components (no NgModule), signals for state
- **Backend**: Environment variables required (see `.env.example`)
- **Database**: PostgreSQL must run before API starts
- **Node version**: Node 25+ required
- **Go version**: Go 1.25+ required
- **SCSS Build Size**: Feature-rich components may exceed default style budgets; update `angular.json` if needed
- **Theme Persistence**: Stored in localStorage under `dashboard-theme` or `theme`
- **Bundle Budget Warnings**: Production build shows 3 warnings (bundle +293.58kB, fonts +3.72kB, styles +1.12kB) — acceptable for current scope
- **Translation Key Sync**: Always keep en.json and bn.json synchronized. Build passes without errors but missing Bangla keys silently fall back to English.
- **Interface compile breaks**: Adding a method to any interface in `interfaces/interfaces.go` breaks all mock structs that implement it. Fix by adding a stub in `payment_service_test.go` (and any other `Mock*` structs for that interface).
